# 概念底座与背景

补充模块，用于回答“为什么建知识图谱”“知识表示到底解决什么”“传统知识表示方法怎么选”“知识图谱与专家系统有什么区别”等问题。它不改变主工作流，但为 Stage 0/1 的判断提供概念依据。

---

## 1. 知识图谱的定位

知识图谱常被同时放在三条脉络里理解：

| 脉络 | 关注点 | 对工程的启示 |
|---|---|---|
| 人工智能 | 语言理解 + 知识表示与推理 | 图谱要能支持语义理解与推理，而不只是存储 |
| 互联网/语义网 | 万物互联、URI、开放数据 | 图谱要有可链接的标识与可交换的表示 |
| 数据库/图计算 | 图结构、查询、图算法 | 图谱要有可查询、可分析、可扩展的存储 |

一句话：**知识图谱是用图结构组织、可被机器查询与推理的知识库。** 它既是数据，也是表示，也是系统。

常见的两类知识：
- **世界知识**：现实世界的实体及其关系（人物、公司、地点、产品、事件）。
- **语言知识**：词、义项、义原、词义关系（WordNet、HowNet）。

其他类型：常识知识、认知知识、领域/行业知识、事件知识、元知识。不同知识类型的获取与表示方法不同，不要用一套 Schema 硬套所有类型。

---

## 2. 知识图谱的价值场景

| 场景 | 机制 | 可测指标 |
|---|---|---|
| 语义搜索 | 事物级而非字符串级检索；实体卡片与关系扩展 | 首条命中率、点击率、查询改写覆盖率 |
| 智能问答 | 结构化答案 + 关系扩展 + 多跳 | 答案准确率、覆盖率、延迟 |
| 推荐 | 用户/物品画像、关系多样性、可解释 | CTR、转化率、多样性、解释采纳率 |
| 语言理解 | 实体链接、常识/领域知识补全 | 下游 NLP 任务指标 |
| 视觉理解 | 实体/场景知识增强识别与检索 | 零样本准确率、检索 Recall@k |
| IoT/设备互联 | 设备数据的语义封装与互操作 | 互操作成功率、集成成本 |
| 大数据分析 | 把分析问题转化为图查询/图算法 | 分析周期、发现率、误报率 |

判断价值时，不要只看“图谱多大”，要看“下游任务提升了多少”。

## 3. 知识表示的五个用途

| 用途 | 含义 | Schema 设计启示 |
|---|---|---|
| 客观事物的机器标识 | 每个事物有唯一标识 | 每类必须有身份规则（URI/主键/组合键） |
| 本体约定与概念模型 | 类型、层次、关系、约束 | 先定类/关系/值域，再灌数据 |
| 支持推理的表示基础 | 能由已知推未知 | 需要规则/公理时选 RDF/OWL/Datalog |
| 高效计算的数据结构 | 机器可快速处理 | 图库/索引/向量表示按查询形态选 |
| 人可理解的机器语言 | 可解释、可审计 | 保留来源、路径、规则；不要只给分数 |

知识表示不等于数据格式、数据结构或编程语言；关键区别是**是否支持推理**。

## 4. 传统知识表示方法

| 方法 | 核心 | 优点 | 缺点 | 与 KG 的关系 |
|---|---|---|---|---|
| 描述逻辑 DL | 概念、关系、个体；TBox/ABox | 形式语义清晰、可判定、可推理 | 表达受限、推理复杂 | OWL 的理论基础 |
| 霍恩规则 | 原子、规则、事实 | 接近自然语言、易精确推理 | 不支持不确定性、组合爆炸 | Datalog/Prolog 的基础 |
| 产生式系统 | IF-THEN + 置信度 | 直观、模块化、可表示不确定性 | 匹配低效、难表达结构 | 专家系统/规则引擎 |
| 框架系统 | 框架 + 槽 + 侧面 | 描述全面、支持数值计算 | 维护成本高、不灵活 | 面向对象/对话系统的前身 |
| 语义网络 | 节点 + 语义边 | 直观、接近联想记忆 | 无公认形式语义、推理不保证 | 知识图谱的直接前身 |

选型提示：
- 需要严格概念包含/实例检测 → 描述逻辑/OWL 子语言。
- 需要业务规则、可读可维护 → Datalog/产生式。
- 需要灵活建模、图分析 → 属性图。
- 需要数据交换/跨组织 → RDF。

## 5. 从知识工程到知识图谱

历史脉络（简版）：
1. 专家系统时代：从专家大脑获取知识，知识库 + 推理引擎；规则明确、边界清晰的场景成功。
2. 瓶颈：人工构建规模有限、专家知识难统一、难精确符号化、开放场景失效。
3. 语义网：用统一表示在互联网上发布与链接数据；强调 URI、本体、开放世界。
4. 现代知识图谱：降低表示严格性、强调规模与自动化获取、拥抱噪声、机器+人工协同。

关键差异：

| 维度 | 传统知识工程 | 现代知识图谱 |
|---|---|---|
| 知识来源 | 专家手工 | 结构化数据 + 自动抽取 + 众包 |
| 表示 | 高表达力逻辑 | 三元组/属性图为主，按需扩展 |
| 规模 | 小 | 百万到千亿级 |
| 质量 | 高但覆盖窄 | 有噪声、覆盖广 |
| 推理 | 严格符号推理 | 符号 + 表示学习 + 规则学习 |
| 成本 | 每条知识很贵 | 边际成本大幅下降 |

工程启示：不要用专家系统时代的“高精度、小规模”思路要求现代图谱；也不要用“大规模、容忍噪声”的思路做高风险决策。

## 6. 典型知识图谱项目（背景）

| 项目 | 类型 | 特点 |
|---|---|---|
| Freebase | 开放世界知识 | 社区协作，后被谷歌收购，曾是 KG 重要数据源 |
| Wikidata | 开放世界知识 | 社区众包、CC0、多语言 |
| DBpedia | 链接数据 | 从维基百科抽取，严格本体 |
| YAGO | 链接数据 | 融合 Wikipedia/WordNet/GeoNames，含时空信息 |
| WordNet | 语言知识 | 同义词集与词义关系 |
| ConceptNet | 常识知识 | 词与词的常识关系 |
| BabelNet | 多语言词典 | 融合 WordNet 与 Wikipedia，多语言 |
| Schema.org | 轻量本体 | 搜索引擎共同推动的 Web 数据 Schema |
| OpenKG | 中文开放图谱 | 中文领域开放知识图谱集合 |

这些项目的价值是“参考 Schema、数据源与治理模式”，不是拿来直接套用。

## 7. 问答的类型与来源

按问句类型：
- 事实型：谁是/哪年/哪里。
- 是非型：是否/有没有。
- 描述型：什么是/介绍一下。
- 列表型：有哪些。
- 比较型：哪个更大/更贵。
- 观点/方法型：为什么/怎么做。

按答案来源：
- 知识图谱问答（结构化）
- 表格问答（半结构化）
- 文本问答（抽取式/生成式）
- 社区问答（问答对）
- 视觉问答（图像/视频）

工程启示：不要用一种问答范式覆盖所有问题；按问题类型路由，答案附来源。

---

## 8. 背景层的反模式

1. 把知识图谱等同于专家系统，要求全量高精度。
2. 把知识图谱等同于数据库，只存不推理。
3. 把“知识”与“数据”混为一谈，忽略推理与语义。
4. 用一套 Schema 覆盖世界知识、语言知识、事件知识。
5. 只讲历史与概念，不落到 Schema/查询/指标。
6. 用典型项目的规模背书自己的领域图谱。

---

## 9. 使用方式

- Stage 0 需要向业务方解释“为什么建图谱”时，用 §2 的价值场景表。
- Stage 1 设计 Schema 时，用 §3 的五个用途检查是否只做了“存储”。
- 选表示方法时，用 §4 的对比表。
- 被问“和专家系统/数据库有什么区别”时，用 §5 的差异表。
- 需要引用典型项目时，用 §6，但不要直接套用其 Schema。
