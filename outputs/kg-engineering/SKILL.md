# 知识图谱工程（KG Engineering）

把“建一个知识图谱”从口号变成可交付工程：先证明值得建，再设计能回答问题的 Schema，然后按阶段选型、构建、融合、推理、评估。

## 使用场景

当用户需要：
- 从零规划一个领域知识图谱（医疗、金融、工业、供应链、内容、政务等）。
- 设计或评审 Schema / 本体 / 实体类型体系 / 关系清单。
- 在属性图、RDF、OWL 之间做表示选型，或在关系库、图数据库之间做存储选型。
- 设计实体识别、关系抽取、属性补全、概念抽取、事件抽取的流水线。
- 做跨源知识融合、本体匹配、实体对齐。
- 做链接预测、知识补全、规则推理、多跳推理。
- 设计 KGQA、语义搜索、知识增强推荐或图分析应用。
- 选择图算法/图神经网络：中心度、社区发现、路径、节点分类、链接预测。
- 构建或使用语言知识图谱：HowNet/义原、词义消歧、义原预测、词典扩展。
- 评估多模态知识图谱、事理图谱、知识增强预训练、联邦/区块链图谱是否值得做。
- 向业务方解释为什么建图谱，或辨析 KG 与专家系统、数据库、语义网的区别。
- 诊断“图谱建了但没人用 / 效果差 / 维护不动”的存量项目。

不要用于：
- 只需要从文档中检索片段、不需要结构化关系的场景（优先 RAG）。
- 纯图论计算（最短路、社区发现）且不涉及知识语义建模的任务。
- 没有数据、也没有明确下游任务的“先建个图谱再说”。
- 单纯的可视化前端或数据大屏需求。

## 输入要求

需要用户提供（缺失时按下述优先级最多追问 3 个问题）：

1. **下游任务**：图谱要支持搜索、问答、推荐、风控、分析还是推理？成功指标是什么？
2. **领域边界**：覆盖哪些实体、哪些关系、哪些时间/地域范围？明确不做什么。
3. **数据资产**：结构化库表、半结构化页面、文本、图片/视频各有多少？是否可持续获取？
4. **规模与增长**：实体数、三元组数、日增量和查询并发。
5. **更新与时效**：知识变化速度、可接受的延迟、是否需要版本与溯源。
6. **可解释与合规**：是否要求推理链、答案出处、权限隔离、隐私保护。
7. **团队与约束**：算法/工程/标注人力、预算、时限、现有技术栈。

若用户未给全，先按最小假设开工，并在交付物开头写明假设；不要因为信息不全而停在空谈。

## 核心原则

1. **任务倒推**：先写“图谱要回答的问题”，再决定建什么。不能落到查询路径上的知识不建。
2. **Schema 先行**：先有类型、关系、约束和身份规则，再有数据。Schema 可以迭代，但不能缺席。
3. **分层建模**：TBox（概念/公理）与 ABox（实例/事实）分开；Schema 与数据分开版本管理。
4. **符号与向量互补**：符号负责精确、可解释、可审计；向量负责泛化、补全、抗噪。不要二选一。
5. **长尾是常态**：冷启动靠结构化数据，规模靠自动抽取，质量靠人机协同；任何“全自动高质量”承诺都不可信。
6. **每阶段有产物和闸门**：没有通过验收产物，不进入下一阶段。

## 工作流

### Stage 0：任务诊断（建不建）

**输入**：下游任务、数据资产、查询样例。

**动作**：逐项打分（0/1），少于 3 分则不建议建 KG：

| 判据 | 通过条件 |
|---|---|
| 关系中心 | 任务的核心是实体之间的关系，而不是单条文本匹配 |
| 多跳需求 | 需要 2 跳及以上关联，或需要聚合/比较/路径解释 |
| 结构化收益 | 结构化后查询精度、速度或可解释性显著优于文本检索 |
| 数据可得 | 已有或可获取实体、关系、属性的稳定来源 |
| 可维护 | 有人负责 Schema、标注、质量与更新 |

**输出**：一页任务卡（目标、用户、查询样例、成功指标、不做什么）。

**失败处理**：若“关系中心”或“数据可得”不成立，改为 RAG/搜索/表格方案，并说明原因。

### Stage 1：能力问题 → Schema

**输入**：任务卡、领域资料、现有词表/本体。

**动作**：
1. 写 10–20 条**能力问题**（competency questions），用用户原话，不写技术术语。
2. 给问题分类：事实型、列表型、比较型、聚合型、多跳型、因果/解释型。
3. 从问题中抽取名词→候选类，动词→候选关系，形容词/数值→候选属性。
4. 合并同义词，确定粒度和类型层次；v1 类型层次建议 ≤ 4 层，关系类型 ≤ 50 个。
5. 为每个类定义**身份规则**（什么算同一个实例）、**必填属性**、**值域**。
6. 选择本体表达力：轻量标签 / RDFS / OWL 2 RL / OWL 2 EL / OWL 2 QL（见选型表）。
7. 建“能力问题—Schema 路径”覆盖矩阵。

**输出**：`schema.md`（类表、关系表、属性表、约束、示例三元组）+ 覆盖矩阵。

**闸门**：每条能力问题都能在 Schema 上写出查询路径；写不出的，要么补 Schema，要么删问题。

**失败处理**：问题无法形式化时，先降级为“检索+摘要”，不要硬造关系。

### Stage 2：表示与存储选型

**输入**：Schema、查询样例、规模、更新模式。

**动作**：
1. 选表示：属性图 / RDF / OWL（见下表）。
2. 选存储：关系库三元组表、属性表、垂直划分表、全索引表、原生图库（见下表）。
3. 选查询语言：Cypher / Gremlin / SPARQL / SQL。
4. 用 3 条代表性查询在 10% 数据上做基准，记录延迟与实现复杂度。

**表示选型表**：

| 条件 | 选择 | 理由 |
|---|---|---|
| 重图结构、路径查询、图算法、边带属性 | 属性图 | 建模灵活、遍历性能好、工业界工具成熟 |
| 重数据交换、跨组织、需要推理与标准 | RDF(S) | W3C 标准、天然支持 URI 与语义查询 |
| 需要类公理、基数约束、传递/互反/函数关系 | OWL 2（按场景选 RL/EL/QL） | 表达力强，可做本体推理 |
| 只需要轻量类型与关系，团队无本体经验 | 属性图 + 轻量 Schema | 降低学习和维护成本 |
| 已有大量关系库且查询简单 | 关系库 + 映射层 | 复用现有运维与工具 |

**存储选型表**：

| 条件 | 选择 | 注意 |
|---|---|---|
| 复杂多跳、路径、子图匹配 | 原生图数据库 | 免索引邻接，遍历复杂度与全局规模无关 |
| 以简单查询为主、已有关系库 | 三元组表/属性表 | 三元组表 Self-Join 多；属性表空值多 |
| 属性差异大、按属性查得多 | 垂直划分表 | 插入跨表多，Subject-Object Join 较弱 |
| 需要多维度索引与压缩 | 全索引（六重索引 + ID 映射） | 写入与存储成本高 |
| 超大规模 + 批处理 | 图计算引擎 + 对象存储 | 与在线图库分工 |

**输出**：`storage-decision.md`（选型、基准查询、容量估算、备份与版本方案）。若选原生图库，必须写明“免索引邻接 + 遍历复杂度”的依据。

**闸门**：3 条基准查询全部可写、可跑、延迟达标；否则回到 Stage 1 调整 Schema。

### Stage 3：知识获取与构建

**输入**：Schema、数据源清单、标注预算。

**动作**（按优先级）：
1. **结构化冷启动**：库表 → R2RML/自定义映射 → 实体与三元组；先建立身份与主键映射。
2. **半结构化补充**：表格、列表、信息框、百科页面；先解析结构，再抽取。
3. **文本抽取**：按 NER → 关系抽取 → 属性补全 → 概念抽取 → 事件抽取 的顺序推进。
4. **多模态补充**：图片/视频中的实体与关系，仅在确有增益时引入。
5. **质量抽检**：每批抽 100–300 条，双人标注 10%，计算一致率与准确率。
6. **人机协同**：模型给候选与置信度，人做接受/拒绝/修正；修正结果回流训练集。

**抽取模型选型**（简表，详见 `references/distilled-framework.md`）：

| 任务 | 低标注/冷启动 | 中等标注 | 高标注/追求效果 |
|---|---|---|---|
| 实体识别 | 词典 + 规则 + 远程监督 | BiLSTM-CRF / CNN-CRF | BERT/Transformer + CRF |
| 关系抽取 | 模板 / Bootstrapping / 远程监督 | PCNN / BiLSTM+Attention | BERT 微调 / 联合抽取 |
| 属性补全 | 规则 + 抽取式 | 抽取式序列标注 | 生成式 + 抽取式融合 |
| 概念抽取 | Hearst 模板 / 百科 | 弱监督序列标注 | 预训练模型 + 类型约束 |
| 事件抽取 | 模式匹配 / FrameNet 弱监督 | DMCNN 两阶段 | 联合结构预测 / 预训练 |

**闸门**：按用途设定指标。搜索/问答类关系抽取准确率建议 ≥ 0.85（抽检），召回率按覆盖率目标定；不达标先降 Schema 范围，不要盲目换更大模型。

### Stage 4：知识融合与对齐

**输入**：多源图谱/数据、Schema 映射、已有对齐种子。

**动作**：
1. **本体匹配**：字符串规范化 → 编辑距离/Dice/Jaccard/TF-IDF → 结构相似度（邻居、层次）→ 人工审核。
2. **实体对齐**：分块（哈希/排序邻居/LSH）→ 候选打分（属性、结构、嵌入）→ 种子对齐 → 迭代扩充。
3. **冲突处理**：同一 `sameAs` 簇内按来源可信度、时间、证据数决策；保留来源与版本。
4. **合并策略**：优先“逻辑合并 + 物理保留”，保证可回滚；不要一上来做物理大合并。

**闸门**：对齐抽检准确率 ≥ 0.95；合并可回滚；冲突有裁决记录。

### Stage 5：推理与补全

**输入**：图谱、查询类型、可解释性要求。

**动作**：
1. 判定推理类型：演绎（规则/本体）、归纳（链接预测/规则学习）、多跳（查询分解/图搜索）、因果/溯因（事理图谱）。
2. 选技术路线（见下表）。
3. 划分训练/验证/测试，采用**过滤式**评测（过滤掉其他真实三元组）。
4. 对高风险推理做人工复核与证据链输出。

**推理选型表**：

| 条件 | 选择 | 风险 |
|---|---|---|
| 规则明确、要求可解释、规模可控 | OWL/Datalog/产生式 + Rete | 规则维护成本高，组合爆炸 |
| 三元组补全、关系预测、有足够训练数据 | TransE/TransR/RotatE 等嵌入 | 稀疏实体效果差，不可解释 |
| 一对多/多对多、属性值预测 | TransR/CTransR/KR-EAR | 参数增多，训练成本上升 |
| 需要多跳逻辑查询/路径证据 | BetaE / PTransE / PRA / AMIE / 强化学习游走 | 路径搜索空间大 |
| 图结构丰富、邻居信息有用 | R-GCN/CompGCN/GraphSAGE | 稀疏图不适用 |
| 新实体、零样本 | DKRL（描述）/ TKRL（类型）/ IKRL（图像） | 依赖外部信息质量 |
| 规则与嵌入都要 | IterE 类迭代框架 | 工程复杂度高 |

**闸门**：推理结果抽检准确率达标；高风险结论必须能给出规则、路径或来源；不能把模型分数当事实。

**图分析分支**（当任务涉及中心度、社区、路径、节点分类、图级任务时）：
1. 先做结构体检：节点/边规模、平均度、连通分量、度分布、同质性、特征覆盖率。
2. 先跑结构基线：度中心度、PageRank、最短路径、随机游走。
3. 再判断是否上 GNN：平均度低、连通性差、无节点特征时，优先 KRL/规则/外部信息。
4. 需要泛化到新节点用 GraphSAGE/GAT；固定图半监督用 GCN；图级任务用层次池化。
5. 详细选型、评测与反模式见 `references/graph-analytics.md`。

### Stage 6：应用与评估

**输入**：图谱、查询日志、下游任务基线。

**动作**：
1. 选应用范式：语义搜索、KGQA、推荐、风控分析、实体分类、信息检索增强。
2. KGQA 四选一或混合：模板、语义解析、检索排序、端到端深度学习（见下表）。无论选哪种，先做实体链接与类型检查。
3. 建端到端评估集：真实问题 ≥ 200 条，覆盖各类能力问题与失败类型。
4. 同时报告**答案正确率、覆盖率、延迟、可解释率、人工接管率**。

**KGQA 选型表**：

| 条件 | 选择 | 优点 | 缺点 |
|---|---|---|---|
| 问题模式固定、要求高准确与低延迟 | 问句模板 + 类型检查 | 精准、快、可控 | 模板维护贵、覆盖窄 |
| 问题多样、可接受解析失败 | 语义解析（逻辑表达式） | 可组合、可解释 | 词典与对齐难 |
| 开放问题、图谱较大 | 检索排序 | 灵活、易融合特征 | 复杂问题弱、答案不保证精确 |
| 有标注问答对、追求端到端 | 深度学习/预训练模型 | 语义表征强 | 需数据、可解释性弱 |
| 生产系统 | 混合：模板兜底 + 解析 + 排序 | 平衡覆盖与精度 | 工程复杂 |

**闸门**：端到端指标超过基线；错误可归因到 Schema/抽取/融合/推理中的具体环节。

**专项分支**：
- 词义级任务（词义消歧、义原预测、词典扩展）→ `references/language-kg.md`。
- 多模态、事理图谱、知识增强预训练、联邦/区块链 → `references/frontier-modules.md`；先做模态消融/小流量 A/B，证明增益再接入。

### Stage 7：交付与迭代

**交付物**：
- `schema.md`、`data-dictionary.md`
- `pipeline/`（ETL、抽取、融合、推理）
- `eval/`（评估集、指标脚本、错误分析）
- `model-cards/`（每个模型的训练数据、指标、局限）
- `ops/`（监控、告警、版本、回滚、权限）
- `blueprint.md`（本项目的完整方案）

**迭代机制**：查询日志 → 未命中/错答聚类 → 回补 Schema 或数据 → 重跑评估；每月至少一次。

## 方法论模块

### M0：概念底座与背景

- 触发：需要解释“为什么建图谱”、KG 与专家系统/数据库的区别、传统知识表示方法选型。
- 步骤：价值场景 → 知识表示的五个用途 → 传统方法对比 → 知识工程到 KG 的差异。
- 输出：一页概念说明或选型依据。
- 常见错误：只讲历史不落地；用专家系统标准要求现代图谱；把 KG 当数据库。
- 详见：`references/concepts-background.md`。

### M1：Schema/本体设计

- 触发：新领域、新应用、类型混乱、关系重复。
- 步骤：能力问题 → 名词/动词抽取 → 归一 → 层次与值域 → 身份规则 → 约束 → 覆盖矩阵。
- 输出：类/关系/属性表 + 示例三元组 + 反例。
- 常见错误：先建类再想问题；类型层次过深；把属性当关系；没有身份规则。

### M2：表示与存储选型

- 触发：技术选型、性能不达标、跨组织交换。
- 步骤：按“查询形态 → 语义需求 → 规模 → 团队”排序，逐项排除。
- 输出：选型表 + 3 条基准查询 + 容量估算。
- 常见错误：默认上 OWL；默认上 Neo4j；忽略写入与运维成本。

### M3：知识抽取流水线

- 触发：从文本/半结构化数据补全图谱。
- 步骤：定义标签体系 → 冷启动 → 远程监督/弱监督 → 多实例 bag + 注意力降噪 → 联合抽取 → 人工校验。
- 输出：抽取模型、置信度、抽检报告、错误类型分布。
- 常见错误：忽略标签体系成本；远程监督不降噪；只报准确率不报覆盖率。

### M4：知识融合与实体对齐

- 触发：多源合并、同一实体多名称、跨语言。
- 步骤：规范化 → 分块 → 相似度/嵌入 → 种子 → 迭代 → 冲突裁决。
- 输出：对齐表、置信度、合并日志、回滚方案。
- 常见错误：全量 O(M×N) 比较；硬对齐导致错误传播；不做分块。

### M5：表示学习与推理

- 触发：链接预测、补全、多跳查询、稀疏实体。
- 步骤：判定关系复杂度 → 选模型 → 负采样 → 过滤式评测 → 误差分析。
- 输出：模型卡、指标（MR/MRR/Hit@n）、稀疏子集表现。
- 常见错误：用 TransE 硬扛一对多；在稀疏图上上 GNN；评测不过滤。

### M6：知识融合后的质量治理

- 触发：图谱上线后冲突、过期、重复。
- 步骤：定义质量维度 → 采样审计 → 冲突检测 → 溯源 → 修复 → 回归。
- 输出：质量看板、问题清单、修复记录。
- 常见错误：只看规模不看一致性；没有来源与时间戳。

### M7：KGQA 与应用

- 触发：搜索/问答/推荐/分析应用。
- 步骤：问题分类 → 范式选型 → 实体链接 → 查询/排序 → 答案生成 → 证据展示。
- 输出：端到端评估、失败归因、人工接管策略。
- 常见错误：只做问句解析不做实体链接；答案无出处；不评估覆盖率。

### M8：前沿能力接入

- 触发：多模态、KG+LLM、事理图谱、低资源。
- 步骤：先证明增益 → 小流量 A/B → 再扩量；保留非 LLM 兜底。
- 输出：增益报告、成本、风险、回退方案。
- 常见错误：把 LLM 当知识库；不做事实校验；忽略延迟与成本。

### M9：图算法与图分析

- 触发：中心度、社区发现、路径、节点分类、图级任务、图神经网络选型。
- 步骤：结构体检 → 结构基线（度/PageRank/最短路/随机游走）→ 判断是否上 GNN → 按直推/归纳与图规模选模型 → 任务指标 + 结构指标评估。
- 输出：结构体检报告、基线对比、模型选型、可解释证据。
- 常见错误：稀疏图上硬上 GNN；忽略边方向与类型；随机切分泄漏；把中心度当业务重要性。
- 详见：`references/graph-analytics.md`。

### M10：语言知识图谱（HowNet/义原）

- 触发：词义消歧、词相似度、义原预测、词典扩展、低频词/未登录词。
- 步骤：确认是词义级任务 → 选现有知识库或自建义原体系 → 人工小规模标注 → 自动预测（协同过滤/矩阵分解/字信息 CSP/跨语言 CLSP）→ 抽检回补 → 下游验证。
- 输出：义原体系、标注规范、预测模型、分频段评估。
- 常见错误：把预测当人工标注；忽略多义词；低频词不用字信息；只报整体 F1。
- 详见：`references/language-kg.md`。

### M11：专项前沿模块

- 触发：多模态、事理图谱、知识增强预训练、知识图谱预训练（PKGM 类）、联邦/区块链。
- 步骤：明确任务与基线 → 数据与预算摸底 → 离线原型 → 小流量 A/B → 证明增益 → 扩量并保留兜底。
- 输出：增益报告、模态消融、成本/延迟、合规与回退方案。
- 常见错误：为多模态而多模态；把 LLM 当知识库；单组织强行上链；公开集代替领域验收。
- 详见：`references/frontier-modules.md`。

## 质量 Rubric

| 维度 | 0 分 | 1 分 | 2 分 | 3 分 |
|---|---|---|---|---|
| 任务对齐 | 无下游任务 | 有目标但无指标 | 有指标与查询样例 | 指标、基线、验收标准齐全 |
| Schema | 无 Schema | 只有类名 | 类/关系/属性/值域齐全 | 有能力问题覆盖矩阵与身份规则 |
| 数据质量 | 无抽检 | 只报模型指标 | 有抽样与错误分类 | 双人标注、一致率、置信度、溯源 |
| 融合 | 未处理多源 | 只做字符串匹配 | 分块 + 多特征 + 人工审核 | 迭代对齐 + 冲突裁决 + 可回滚 |
| 推理 | 无推理 | 只用模型打分 | 符号/向量按场景选型 | 混合推理 + 证据链 + 高风险复核 |
| 可解释 | 无来源 | 只有答案 | 有路径/规则/来源 | 可审计的推理链与置信度 |
| 工程 | 脚本堆叠 | 有 ETL | 有版本、监控、回滚 | 有 SLA、容量规划、权限与成本模型 |
| 评估 | 无评估 | 只用公开集 | 有领域评估集 | 端到端 + 分阶段 + 错误归因闭环 |

交付阈值：总分 ≥ 18/24；任务对齐、Schema、数据质量、评估不得低于 2 分。

## 反模式

不要：
1. 没有下游任务就开建。
2. 先写代码后补 Schema。
3. 把属性（性别、国籍）当普通关系硬套平移模型。
4. 所有场景都上 OWL 全公理。
5. 默认“图数据库一定比关系库快”。
6. 用全量笛卡尔积做实体对齐。
7. 远程监督标注后不降噪。
8. 只报准确率，不报覆盖率与召回率。
9. 用未过滤的链接预测指标吹效果。
10. 在高度稀疏的图上直接上 GNN。
11. 把嵌入模型的分数当事实。
12. 用硬对齐合并实体且不可回滚。
13. KGQA 只做问句解析，不做实体链接与类型检查。
14. 答案不给来源与时间。
15. 把 LLM 生成内容直接写入图谱。
16. 没有标注规范就让人工标。
17. 只建图不做查询日志与反馈闭环。
18. 用公开数据集指标代替领域验收。
19. 忽略写入、更新、删除与版本。
20. 把“图谱规模”当唯一 KPI。
21. 在稀疏图上硬上 GNN，或忽略边方向/类型。
22. 用随机切分评估图模型，造成节点/边泄漏。
23. 把义原预测结果直接当人工标注，或忽略多义词。
24. 为多模态/事理图谱/区块链而做，不做基线对比与回退设计。

## 来源与边界

蒸馏自两本知识图谱教材的方法体系（内部证据索引见 `references/evidence-map.md`），并做了跨书融合与工程化改写。成品不包含原书长段原文。

模块文件：
- `references/concepts-background.md`：概念底座（价值场景、五个用途、传统知识表示、知识工程演进、典型项目、问答类型）。
- `references/distilled-framework.md`：核心框架（表示/存储/抽取/表示学习/融合/推理/应用）。
- `references/graph-analytics.md`：图算法、图表示学习、GNN、KG+GNN。
- `references/language-kg.md`：HowNet/义原、义原预测、词典扩展、义原驱动语言模型。
- `references/frontier-modules.md`：多模态、事理图谱、知识预训练、低资源、联邦/区块链。
- `references/quality-rubric.md`：阶段闸门与指标口径。
- `references/evaluation-datasets.md`：链接预测/抽取/QA/语言 KG/GNN 的常用数据集与坑。
- `references/coverage-report.md`：覆盖审计（原书知识点 vs Skill）。
- `templates/kg-blueprint.md`：项目方案模板。
- `scripts/`：Schema 校验、抽取评估、链接预测评估（见 `scripts/README.md`）。

边界：
- 本 Skill 提供方法论与决策框架，不保证在未经验证的数据上达到具体指标。
- 具体模型效果依赖数据分布、标注质量与算力；选型表给出的是默认起点，不是定律。
- 涉及医疗、金融、法律等高风险领域时，必须引入领域专家复核与合规审查。
- 大模型/多模态方案迭代快，接入前需做小流量验证与回退设计。
